## 何时调用

每次制作人认为一项任务、切片、阶段或整版可以完成时，先实际调用全部三位评审。可优先委派小衡（`game-review-panel`）这个[总入口](independent-reviewers/README.md)组织三人独立执行；小衡不投票，制作人仍负责原有完成决定及状态记录。包括准备给出“带明确遗留通过”的情况；不能换成“基本完成”“已交付”来绕过。

日常开发进展、内部草稿和 submitted 可以继续记录为进行中或待审，不等于任务完成。设计、研究或其他非代码交付也要经过此门：提供该任务产物和它对应的当前实际游戏，不能把文档当游戏来回答付费或商业质感问题。没有足够游戏证据时评审可回证据不足，制作人保持待审，不编造可玩版本或自设免审种类。

占位阶段仍遵守原路线和前置条件，不因求票擅自启动被禁止的美术生产、商业化、付费系统或额外范围。原型可能过不了本次更严格的完成门，应如实记录和修复；若与用户已设前置门发生无法自主解决的冲突，说明冲突和最小选择，不降分数线、不冒称商业成品质感已达标。

## 执行顺序与独立性

1. 技术线按当前项目实际 Git / 远端能力执行共享工作流的隔离交付、独立 review 与集成；具备条件时沿用 worktree / PR 流程，无远端或无 Git 时保留明确差异/文件清单和独立审查，不伪造 PR。需要正式验收的任务由独立 `game-verifier` 对明确版本执行 acceptance。技术正确与三人评审分别保留。
2. 制作人冻结一份候选：`task_id`、任务范围、`round_id`、`candidate_id`、证据清单及设备/视口。已提交代码用完整集成 SHA 并补构建/资产标识；无 Git、含未提交代码或非代码产物时，用不可混淆的实际内容/构建版本或摘要锁定。未提交差异须明确，不能只用 HEAD 代表整个候选，不伪造 SHA。证据截图、录屏、试玩入口、已测范围与缺项一并提供。
3. 实际创建三位不同评审实例，分别交付相同材料包和各自角色指令。优先使用已安装的命名角色；若当前会话未识别，读取对应 TOML 的完整 `developer_instructions` 交给新普通子 agent，记录此降级方式，不能仅改显示名。每一轮含复审均使用干净上下文，工具支持时设置 `fork_turns="none"`，不把作者自评、期望票数、旧轮票或其他两人的结论带入。无法隔离时须说明限制并保持待审，不能冒称独立盲评完成。
4. 并发不足可分批，但保持同版同包，先结束无任务实例。三份独立结果全部收齐才计票；制作人不能自填缺票或让一位 agent 扮三票。被评作品实现者不能同时担任其独立评审。
5. 制作人或受委派的小衡将原报告链接和原始票据保留在项目既有证据位置，运行本地票门检查；制作人核对执行记录与原报告后按下述规则记录，不只留一个总分或口头“大家认可”。完成后释放评审实例。

评审意见可以返回修改建议，但评审不能自己改作品再评自己。制作人仍负责派修和记录，专业领域仍平权；两票门不让制作人自行推翻美术结论或冒充另一张玩家票。

凡评审未通过（reject/revise/insufficient），原报告须单列“不通过原因与复评条件”，逐项给出问题及性质、证据位置、体验/质感影响、最小优化方向和可观察复评条件。所有实际硬否决及10元/商业门的否定必须逐项有依据，不能只留分数或“质感差、不值10元”；缺证列最小补证内容，个人偏好另列。小衡汇总完整保留各人拒绝点，制作人据此将实际整改派给对应专业角色；评审不直接改作品。解释不足只向原评审补询其已有判断，不能代写理由、诱导改票或拼旧票；复评仍遵守新轮同版全评规则。即使两票通过，也保留第三人的问题，不把个人反对升级为全局一票否决。

## 计票与完成决定

- 只有 `decision=pass` 且本角色必答门满足的票算通过；`revise`、`reject`、`insufficient` 均不算。没运行、超时、失败或没有报告属于缺票，不能冒充 `insufficient` 回票。
- **三人均已评定且至少两票有效通过，此评审门才通过。** 一人否决只是该角色不给通过票；两票通过加一票否决可以通过本门，不擅自改成三票全过或专家一票全局否决。第三人的问题保留，不删除或包装为认同。
- 整体完成 = 原有独立验收及适用前置/真人/平台门满足 **并且** 本次三人门通过。两票不能盖过崩溃、功能验收失败、未满足的必需真机证据或其他已承诺阻断。
- 票数不足时维持待审/未通过，继续修复、补证和不依赖该完成的工作；不能推进依赖此门的后续阶段，也不能用“带遗留通过”变相放行。
- 同一版本同一证据不重复抽票，不换实例直到凑出两票。只有实质修复、新证据或可核查纠错才另建 `round_id` 复审，写明差异、保留旧轮；候选或关键材料变化后全部三人重评，不拼接旧票。票据篡改不是纠错。

每位评审内部的判定优先级：已证实硬否决 → 关键证据不足（附局部修改意见）→ 证据齐备但需修改 → 通过。此优先级决定个人票，不改变全局 2/3 规则。

## 票据格式与本地检查

制作人收集评审原样输出，组织成 JSON 文件；字段如下。示例只说明结构，不是一轮已经获得的评审。

```text
schema_version: 1
task_id: 本次任务标识
round_id: 本轮唯一标识
candidate_id: 锁定的提交/构建/内容版本
evidence_ids: 非空且不重复的材料标识列表
ballots: 三份票，各自包含：
  reviewer_id: 三个指定角色之一且各一份
  role_version: "1.1"
  task_id / round_id / candidate_id: 精确匹配材料包
  evidence_ids: 本票实际引用的包内材料；缺证票可为空，通过票不可为空
  decision: pass | revise | reject | insufficient
  gate_answer: yes | no | unknown
  gate_reason: 对必答问题的具体依据，非空
  hard_rejections: 已证实硬否决编号列表，无则空；每项在原报告给证据
  details_ready / commercial_ready: 仅专业美术票必填，yes | no | unknown
```

玩家 `gate_answer=yes` 对应明确“愿意”；no 对应“不愿意”，必须 reject；unknown 对应“证据不足”，无其他已证实硬否决时必须 insufficient。专家两分项任一 no 则总门 no；没有 no 但有 unknown 则 unknown；全 yes 才是 yes。yes 只是必要条件，其他标准没过依然不能 pass。

`hard_rejections` 只能采用本角色合法编号：玩家 V1/G1/U1/T1/P10；专家 A1/A2/A3/A4/C1。有已证实硬否决时必须 reject 且实际引用证据；unknown + reject 仅在有此证据及合法硬否决编号时有效，例如截图已证实V1但玩法/付费未验证。不能把未知付费写成P10（P10要求no），C1要求至少一专业分项为no。pass/revise/insufficient不能同时声明已证实硬否决；硬否决规则不要求评审编造未知项答案。

```powershell
python "<实际票门脚本绝对路径>" "<实际票据.json>"
```

整套团队入口 `$game-team` 使用包内 `scripts/review_gate.py`；独立调用小衡可用 `<个人agents目录>/game-review-panel/review_gate.py`；在源码仓库可用 `tools/review_gate.py`。定位后传实际绝对路径，无需固定盘符。默认个人目录为 `CODEX_HOME/agents`，未设置时为 `~/.codex/agents`。这些脚本由安装器保持原字节一致；不要另写放宽版检查。小衡可组织票包和运行检查，但不能改写原票或取代制作人的整体完成判断。

退出 0 表示三人门通过；1 表示三票有效但不足两票；2 表示缺票、格式或版本/轮次绑定不合法。输出 `quality_gate` 为 `passed` / `not_passed` / `invalid`。脚本只校验票据和计票，不能证明材料真实、评审确已独立运行或真人真的会付款；原报告和可核查证据仍是必需品。

## 与看板和状态的连接

当前项目已明确接入看板时，继续只有原八岗位进行 v1 上报。三名评审不注册看板岗位，不借用 verifier 或 developer 身份，不发送 verification。制作人通过已有 checkpoint 的 summary/evidence 引用任务/候选/轮次、三份报告、三张票、计数与未通过原因；原 `game-verifier` 的 verification 仍只表达其实际验收范围。未接入项目保留本地原报告、票据与检查，不虚构run或要求接入云端，独立验收和三人完成门仍须执行。

只有完整完成门通过后，制作人才在原 STATE 记录完成及适用的阶段推进。可以先记录“功能验收通过，三评审待审/未通过”，不能把前者缩写为整个任务通过。尚未运行评审时不得填样例票、补写历史通过或为验证配置而改任何游戏进度。
